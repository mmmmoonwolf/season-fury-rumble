# เล่นข้ามเครื่อง (netplay) — สิ่งที่รู้จากการเล่นจริง

> **สถานะ: เล่นได้แล้ว** ทดสอบจริง iPhone 11 (host) กับ iPhone 17 Pro Max
> เจอสองบั๊ก แก้แล้วทั้งคู่ · ยังมีข้อจำกัดเรื่องหน่วงที่ยังไม่แก้ (ดูท้ายไฟล์)

วิธีทำงานอยู่ใน `src/modes/scramble/netplay.js` — lockstep แบบหน่วงอินพุต ส่งแค่ปุ่มที่กด

## บั๊กที่ 1 · เกมวิ่งเร็วเกิน

**อาการที่ผู้เล่นเจอ**: "ภาพวิ่งกันเร็วมากๆ เหมือนกดคูณ 3"

`tickNet()` เขียนไว้ว่า:

```js
let budget = 4;                                  // เผื่อไว้ตอนไล่ตามหลัง
while (budget-- > 0 && this.net.ready()) { ... }
```

เจตนาคือ "เผื่อไว้ตอนตามหลัง" **แต่ lockstep จองอินพุตล่วงหน้า `delay` เฟรมอยู่แล้วทั้งสองฝั่ง**
(`pushLocal` เติมคิวถึง `frame + delay`) `ready()` จึงเป็นจริงติดกัน `delay + 1` เฟรม **ตลอดเวลา**
ไม่ใช่แค่ตอนตามหลัง

`update()` มี accumulator คุมให้ `tick()` มา 60 ครั้ง/วินาทีอยู่แล้ว
เดินซิม 4 เฟรมต่อ tick จึงแปลว่าซิมวิ่งเกินความเร็วจริง — **วัดในเทสต์ได้ 2 เท่าพอดี**
(ไม่ถึง 4 เท่าเพราะยังถูก `ready()` คุมอยู่บางจังหวะ)

**ไม่เกี่ยวกับรีเฟรชเรตของจอ** — iPhone 17 Pro Max 120 Hz กับ iPhone 11 60 Hz
ได้ tick 60 ครั้ง/วินาทีเท่ากันเพราะ accumulator แปลง delta เป็นเฟรมให้ บั๊กนี้เกิดกับทุกคู่เครื่อง

### ทางแก้

เดินหนึ่งเฟรมต่อ tick เป็นหลัก เดินเกินได้เฉพาะตอน **ตามหลังจริง**
คือคิวของอีกฝั่งกองไว้เกินระยะจองล่วงหน้า:

```js
const lead = this.net.behind - (this.net.delay + 1);   // หักระยะจองที่มีอยู่ตลอดเวลาออกก่อน
let budget = 1 + Math.max(0, Math.min(NET_CATCHUP, lead));
```

ไม่หัก `delay + 1` ออก ทุก tick จะดูเหมือนตามหลังอยู่เสมอ แล้วเร่งทิ้งทุก tick

## บั๊กที่ 2 · เอฟเฟคค้างบนจอ กองสะสม

**อาการที่ผู้เล่นเจอ**: "effect ฟันค้าง ไม่หายไปจากหน้าจอ ยิ่งเอฟเฟคเพิ่มมากเท่าไรยิ่งค้างสะสม"

`tick()` ขึ้นต้นด้วย:

```js
tick() {
  if (this.net) { this.tickNet(); return; }    // <-- ทุกอย่างใต้นี้ไม่ทำงานตอนต่อเน็ต
```

ใต้บรรทัดนั้นมีทั้งการแปลอีเวนต์เป็นภาพ/เสียง **และตัวนับอายุอนุภาค** (`_stepFx`)
ขณะที่ **รอยฟาดถูกยิงจาก `draw()`** (`slashFor` ใน `_drawCharSprite`) ซึ่งทำงานอยู่ตลอด

= มีคนสร้างอนุภาค แต่ไม่มีใครนับอายุ → ค้างบนจอไปเรื่อย ๆ ไม่มีวันหาย ยิ่งตียิ่งสะสม

### ทางแก้: แยก `tick()` เป็นสามส่วน

| ส่วน | เรียกเมื่อไหร่ | ทำอะไร |
|---|---|---|
| เดินซิม | ต่อ tick | ออฟไลน์เดินเอง · ต่อเน็ตเดินผ่าน `tickNet()` |
| `_simEvents()` | **ต่อหนึ่งเฟรมของซิม** | แปลอีเวนต์เป็นป้ายเลข เสียง จอสั่น อนุภาค |
| `_ageFx()` | ต่อ tick | นับอายุอนุภาค ประกาย ป้ายเลข |

`_simEvents()` ต้องเรียกต่อ **หนึ่งเฟรมของซิม** ไม่ใช่ต่อ tick เพราะ `sim.events` ถูกล้างทุก `step()`
tick ที่ไล่ตามหลังแล้วเดินสามเฟรม ถ้าเรียกท้าย tick จะเหลืออีเวนต์เฟรมสุดท้ายเฟรมเดียว
ป้ายเลขดาเมจจะหายไปสองในสาม

**ของแถม**: ตอนต่อเน็ตเพิ่งมีป้ายเลขดาเมจ เสียง และจอสั่นเป็นครั้งแรก (เดิมไม่มีเลย)

## ทำไมเทสต์ 1233 ข้อเดิมจับไม่ได้ทั้งสองอัน

เทสต์ netplay เดิมถามว่า **"สองเครื่องเห็นตรงกันไหม"** ซึ่งตอบว่าตรง และตรงจริง

มันตั้งใจไล่เดินให้เร็วที่สุดเพื่อเทียบสถานะ — `while (lsA.ready() && lsB.ready())` ไม่มีเพดาน
**คำถามว่า "เดินเร็วเท่าที่ควรไหม" ไม่มีใครเคยถาม** และ `tickNet()` (ซึ่งเป็นที่ที่บั๊กอยู่)
ไม่เคยถูกเทสต์เลยแม้แต่ครั้งเดียว — เทสต์เรียก `Lockstep` ตรง ๆ ข้าม `tickNet` ไป

ทำนองเดียวกัน ไม่มีเทสต์ไหนถามว่า "ตอนต่อเน็ต โค้ดฝั่งภาพถูกเรียกครบไหม"

`tick_rate.test.mjs` ถามสองข้อนั้นตรง ๆ และ **ลองใส่บั๊กเดิมกลับเข้าไปแล้วทั้งคู่**:
`budget = 4` → ฟ้องสามข้อ (โชว์ 240 เฟรมใน 120 tick) · `return` → ฟ้องว่านับอายุ 0/5 ครั้ง

## ข้อจำกัดที่ยังไม่แก้: หน่วงมากกว่าระยะจอง = เกมเดินช้ากว่าเวลาจริง

lockstep เดินเฟรม F ได้ก็ต่อเมื่ออินพุตเฟรม F ของอีกฝั่งมาถึง
อีกฝั่งส่งเฟรม F ตอนมันอยู่เฟรม `F - delay` แล้วใช้เวลาเดินทาง `lag`

**ถ้า `lag > delay` เกมจะเดินช้ากว่าเวลาจริงโดยหลีกเลี่ยงไม่ได้** ราว `delay / (lag + delay)`
วัดจากเทสต์ (`delay` = 3):

| หน่วงทางเดียว | ความเร็วที่ได้ |
|---|---|
| 1 เฟรม (~17 ms) | 99% |
| 3 เฟรม (~50 ms) | 79% |
| 6 เฟรม (~100 ms) | 48% |

100 ms ทางเดียวเป็นเรื่องปกติของเน็ตมือถือ ถ้าเจอ **อาการจะเป็น "ช้าและกระตุก" ไม่ใช่เร็ว**

**ทางแก้ที่ยังไม่ได้ทำ**: ปรับ `delay` ตามหน่วงที่วัดได้จริง (แลกกับปุ่มหน่วงขึ้น)
`delay` เป็นค่าของแต่ละเครื่องล้วน ไม่ได้เข้าไปในซิม จึงปรับได้ฝ่ายเดียวโดยไม่ต้องตกลงกับอีกฝั่ง
และไม่กระทบ desync เลย

**เร่งให้เดินเกินหนึ่งเฟรมต่อ tick ไม่ใช่ทางแก้** — มันคือบั๊กที่ 1 นั่นเอง
แก้อาการช้าได้จริงแต่แลกด้วยเกมวิ่งเร็วเกินตอนเน็ตดี ทั้งคู่คือความเร็วผิด

## วิธีตรวจตอนเทสจริง

กด **F** (หรือปุ่ม `Hz`) เปิดตัววัด — กดได้ตอนต่อเน็ตแล้ว โชว์สามค่า:

```
จอวาด 60/วิ · เกมเดิน 60 เฟรม/วิ · ความเร็ว 1.00x
```

- **ความเร็ว ≈ 1.00x** = ถูก · มากกว่า = บั๊กแบบที่ 1 กลับมา · น้อยกว่า = หน่วงเกินระยะจอง
- **จอวาด** บอกรีเฟรชเรตจริงของเครื่องนั้น (120 บน ProMotion) ซึ่งไม่ควรมีผลกับ "เกมเดิน"

## เล่นจบแล้วเล่นต่อในห้องเดิม — เลขแมตช์ (epoch)

เดิม **ต่อเน็ตแล้วกลับไปหน้าเลือกตัวไม่ได้เลย** ทางเดียวคือรีเฟรชหน้าเว็บแล้วเข้าห้องใหม่
ซึ่งเป็นเหตุผลเดียวที่ปิดบังบั๊กข้างล่างไว้ได้ตลอดมา — การรีเฟรชสร้าง `Lockstep` ใหม่ทั้งตัว

### บั๊กที่รออยู่: `sim.frame` รีเซ็ต แต่ `Lockstep.frame` ไม่รีเซ็ต

`beginMatch()` ตั้ง `sim.frame = 0` ทุกครั้งที่เริ่มแมตช์ แต่ `Lockstep` เดินเลขของตัวเองต่อ
แมตช์ที่สองจึงไป `take()` อินพุตที่เลขเฟรมหลักร้อย ซึ่งเป็นของแมตช์ที่แล้ว

ไม่ throw ไม่ค้าง ไม่มีอะไรฟ้องเลย — แค่สองเครื่องเห็นคนละเกม

### ทางแก้: `Lockstep.reset(epoch)` + ฟิลด์ `m` ในทุกแพ็คเก็ตอินพุต

`reset()` ล้างคิวทุกที่นั่ง ตั้ง `frame = 0` และ `sent = -1` — แต่แค่นั้นยังไม่พอ

**ตอนแมตช์ก่อนจบ อีกฝั่งยังส่งอินพุตของเลขเฟรมเก่าค้างอยู่ในสาย** ถ้าล้างคิวแล้วรับมันเข้ามา
มันจะกลายเป็นอินพุตของแมตช์ใหม่ที่เลขเฟรมทับกันพอดี ตรวจด้วยเลขเฟรมอย่างเดียวไม่ได้
ทุกแพ็คเก็ตจึงพกเลขแมตช์ (`m`) มาด้วย และ `onPacket()` ทิ้งอันที่ไม่ใช่ epoch ปัจจุบัน

**เลขแมตช์มาจากโฮสต์เสมอ** ส่งมาในแพ็คเก็ต `go` ก้อนเดียวกับตัวละครและค่าปรับจูน
ต่างคนต่างนับแล้วเหลื่อมกันเมื่อไหร่ อินพุตของอีกฝั่งจะถูกทิ้งทั้งหมด = ค้างรอตลอดกาล

### กลับกัน: แพ็คเก็ตของแมตช์ **ถัดไป** ที่มาถึงก่อนเวลา ห้ามทิ้ง

อีกฝั่งอาจประมวลผล `go` เสร็จก่อนเราเสี้ยววินาที แล้วยิงเฟรม 0..delay-1 ของแมตช์ใหม่มาทันที
ทิ้งไป = เขารอเฟรม 0 ของเรา เราก็รอเฟรม 0 ของเขาที่ถูกทิ้งไปแล้ว **ค้างกันตลอดกาลทั้งคู่**

`onPacket()` จึงพักของที่ epoch สูงกว่าไว้ใน `pending` (มีเพดาน 64 กันคิวโตไม่หยุด)
แล้ว `reset()` เทกลับเข้าคิวให้ตอนขึ้นแมตช์นั้นจริง

### และห้ามล้างคิวตอนเริ่มแมตช์ **แรก**

เหตุผลเดียวกันแบบกลับด้าน: อีกฝั่งกดพร้อมก่อนเราแล้วส่งเฟรมต้น ๆ มาระหว่างที่เรายังเลือกตัวอยู่
`beginMatch()` จึงล้างเฉพาะตอนเลขแมตช์เปลี่ยนจริง (`if (net.epoch !== ep) net.reset(ep)`)

### ทางกลับหน้าเลือกตัวมีสองทาง ทั้งคู่พาไปทั้งสองฝั่ง

1. **เมนูหยุดพัก → "กลับไปเลือกตัวละคร"** ส่งแพ็คเก็ต `lobby` แล้วเปิดหน้าเลือกตัวทั้งคู่
2. **จบแมตช์เอง** ค้างป้ายผู้ชนะไว้ `MATCH_END_HOLD` เฟรม **ของซิม** แล้วไปเอง

ข้อ 2 นับเป็นเฟรมของซิมไม่ใช่มิลลิวินาที เพราะเฟรมของซิมคือเส้นเวลาเดียวที่สองเครื่องใช้ร่วมกัน
นับด้วยเวลาจริงเมื่อไหร่ เครื่อง 60 Hz กับ 120 Hz จะกลับคนละจังหวะ แล้วฝั่งที่กลับก่อน
หยุดส่งอินพุต ทำให้อีกฝั่งค้างอยู่หน้าจอจบไปอีกพักหนึ่งโดยไม่มีเหตุผลให้เห็น
(แพ็คเก็ต `lobby` ที่ส่งตอนนั้นเป็นแค่ตาข่ายรอง เผื่อฝั่งไหนไม่ถึงเส้นด้วยตัวเอง)

**ฝ่ายเดียวกลับไปเลือกตัวไม่ได้เด็ดขาด** lockstep เดินด้วยอินพุตของทั้งสองฝั่ง
ฝั่งที่ยังอยู่ในสนามจะค้างรอเฟรมที่ไม่มีวันมา แล้วอ่านว่า "เกมแฮงก์" ไม่ใช่ "เพื่อนออกไปแล้ว"

### ของที่ถอดออกพร้อมกัน: "จบแมตช์แล้วกดตีเริ่มใหม่"

`updateMatch()` เคยเริ่มแมตช์ใหม่ให้ทันทีถ้าใครกดปุ่มตีตอนป้ายผู้ชนะขึ้น
พอมีทางกลับหน้าเลือกตัวแล้ว มันกลายเป็น**ปลายทางที่สอง** ที่เดาไม่ได้:
มาสห์ปุ่ม = ได้แมตช์ใหม่ด้วยตัวเดิม · ปล่อยไว้เฉย ๆ = ได้หน้าเลือกตัว

ตอนนี้เหลือปลายทางเดียว และปุ่ม "พร้อม/เริ่ม" บนหน้าเลือกตัวคือปุ่มเริ่มใหม่
ซึ่งเห็นอยู่ มีป้ายกำกับ และไม่ต้องเดา

### ความเข้ากันได้กับบิลด์เก่า

แพ็คเก็ตที่ไม่มีฟิลด์ `m` ถือว่าเป็นแมตช์ที่ 0 ซึ่งตรงกับค่าเริ่มต้น
แท็บเก่าจึงยังเล่น**แมตช์แรก**กับแท็บใหม่ได้ปกติ (แมตช์ที่สองไม่ได้ เพราะมันไม่รู้จัก `lobby`)

## เล่นสี่คน (2v2 ข้ามเครื่อง) — ท่อแบบดาว

`Lockstep` รองรับ N ที่นั่งมาตั้งแต่ต้นแล้ว สิ่งที่ขาดคือ **ท่อ** ซึ่งรับได้แค่สองคนต่อห้อง

### ทำไมเป็นดาว ไม่ใช่ตาข่าย

ตาข่ายต้องให้แขกทุกคนรู้จัก peer id ของแขกคนอื่น ซึ่งต้องมีใครสักคนบอก = ต้องมีตัวกลางอยู่ดี
และเพิ่มทางที่ต่อไม่ติดจาก 1 เส้นเป็น 6 เส้น (วง wifi ที่บล็อก WebRTC บล็อกทีละคู่ ไม่ใช่ทั้งห้อง)

เจ้าของห้องเป็นศูนย์กลาง: แขกคุยกับเจ้าของห้องคนเดียว **เจ้าของห้องส่งต่อให้แขกที่เหลือ**
(`relay()` ใน session.js) ส่งต่อทุกชนิดแพ็คเก็ต ไม่ใช่แค่อินพุต — เลือกตัว/กดพร้อม
แขกคนอื่นก็ต้องเห็นเหมือนกัน ไม่งั้นแขกสองคนไม่มีวันรู้จักกันเลย

**ราคาที่จ่าย: แขกถึงแขกเดินสองต่อ** หน่วงเป็นสองเท่าของแขกถึงเจ้าของห้อง
ซึ่งอาจต้องเพิ่ม `NET_DELAY` ตอนเล่นสี่คนจริง — **วัดก่อนค่อยปรับ อย่าเดา** (กด F ดูตัวคูณความเร็ว)

### ที่นั่งมาจากเจ้าของห้อง ไม่ใช่เดาเอง

แขกเดาที่นั่งตัวเองไม่ได้ เพราะไม่รู้ว่ามีใครเข้ามาก่อนหรือยัง
เดาซ้ำกันเมื่อไหร่ **สองเครื่องจะคุมตัวละครตัวเดียวกัน** โดยไม่มีอะไรฟ้อง

เจ้าของห้องแจกตอน `conn.on("open")` เป็นแพ็คเก็ต `{t:'seat', seat, seats}`
ซึ่ง session.js กินเอง ไม่ส่งต่อให้ฉาก (เป็นข้อมูลของชั้นท่อ ไม่ใช่ของเกม)

**แขกยังเข้าเกมไม่ได้จนกว่าจะได้ที่นั่ง** — ฉากสร้างคิวอินพุตจากเลขที่นั่งตั้งแต่เฟรมแรก
แก้ทีหลังไม่ได้ ใช้นาฬิกาหมดเวลาตัวเดิมที่เดินอยู่แล้ว ไม่ตั้งเพิ่ม
(เพิ่มตัวที่สอง = มีระเบิดเวลาอีกลูกที่ต้องจำว่าต้องยกเลิกตรงไหนบ้าง)

### กับดักที่อันตรายที่สุด: ธง `ai`

`setRoster(4)` ติดธง `ai` ให้ช่อง 3-4 ไว้ เพราะมันถูกออกแบบมาสำหรับ 2v2 **บนเครื่องเดียว**
ที่สองช่องหลังเป็นเพื่อน AI

ต่อเน็ตทุกช่องมีคนจริงนั่งอยู่ `startNet()` จึงต้องปลดธงทุกช่อง
ลืมปลด = ซิมเอาอินพุตของ AI ไปใช้แทนอินพุตที่ส่งข้ามเน็ตมา (ดู `step()`)
สองเครื่องคิดคนละอย่างตั้งแต่เฟรมแรก ไม่ throw ไม่ค้าง ไม่มีอะไรฟ้อง

### พร้อมครบทุกที่นั่งถึงจะเริ่ม

เดิมเช็ค `myReady && foeReady` ซึ่งเป็นคำที่มีความหมายเฉพาะตอนสองคน
ตอนนี้เป็น `_notReady()` คืนลิสต์ที่นั่งที่ยังไม่กด — ใช้ทั้งตัดสินว่าเริ่มได้
และบอกคนเล่นว่า "รอผู้เล่น 3, 4" เป็นตัวเลข ไม่ใช่ "รออีกฝั่ง"

ล็อบบี้ก็เหมือนกัน: ห้องสี่คนไม่เข้าเกมจนกว่าจะครบ
เข้าไปตอนยังไม่ครบ = ที่นั่งที่เหลือไม่มีใครส่งอินพุต lockstep ค้างรอตลอดกาล
ซึ่งบนจออ่านว่า "เกมแฮงก์" ไม่ใช่ "ยังรอเพื่อนอยู่"
